 (Merchant Integration Module)

1. Введение

Модуль расширяет существующий криптокошелёк (Node.js, multi-chain) и превращает его в платёжный шлюз. Мерчанты получают возможность принимать криптовалюту на своих сайтах через API платформы без необходимости самостоятельно управлять кошельками и мониторингом.

2. Назначение модуля

- Дать мерчантам простой способ подключения приёма криптоплатежей.
- Предоставить выбор между двумя моделями генерации адресов.
- Обеспечить удобное управление несколькими магазинами из одного кабинета.
- Реализовать контролируемый вывод средств (payout) с очередью и ручной/полуавтоматической обработкой.

3. Ключевые термины

- Магазин — отдельная интеграция мерчанта (один сайт/проект) со своими настройками, API-ключом и балансом.
- API-ключ магазина — ключ для аутентификации запросов от backend’а мерчанта.
- Постоянный адрес — один и тот же адрес выдаётся одному пользователю мерчанта (по user_id).
- Временный адрес — новый адрес генерируется для каждого платежа/заказа с ограниченным временем жизни.
- Заявка на выплату — запрос мерчанта на вывод средств с внутреннего баланса магазина на внешний адрес (проходит через очередь и получает статусы).
- Генерация инвойс ссылки - при запросе на пополнение, выдаеться открытая ссылка на оплату на стороне шлюза со своим дизайном, регистрирует платеж от пользователя и возвращает статус платежа если оплата прошла и платеж дошел возвращая хеш успешной оплаты.

4. Функциональные требования


4.1. Подключение магазина

В личном кабинете мерчант создаёт магазин → указывает название и домен → получает API-ключ и доступ к инструкциям по интеграции. Домен используется для привязки и валидации.

4.2. Управление несколькими магазинами

Мерчант может подключить несколько магазинов в одном аккаунте. В кабинете есть удобный переключатель между ними. При переключении отображаются отдельные баланс, статистика, история платежей и настройки каждого магазина.

4.3. Режимы генерации адресов

В настройках каждого магазина переключается режим:
Аспект
Постоянный кошелёк
Временный кошелёк
Когда использовать
Подписки, лояльность, пользователи
Разовые покупки, высокая приватность
Идентификация
По адресу (user_id)
По order_id / payment_id
Приватность
Средняя
Высокая
Количество адресов
Минимальное
Максимальное

Переключение режима влияет только на новые запросы генерации адресов. Существующие постоянные адреса остаются рабочими.

4.4. Процесс приёма платежей (высокоуровнево)

1. Плательщик оформляет заказ на сайте мерчанта.
2. Backend мерчанта запрашивает адрес у платформы (передаёт user_id или order_id + сеть).
3. Платформа возвращает адрес (и QR, expiration при временном режиме).
4. Плательщик переводит криптовалюту.
5. Система мониторинга платформы фиксирует транзакцию и подтверждения.
6. Средства зачисляются на внутренний баланс магазина.
7. Мерчант получает уведомление (webhook или polling).

4.5. Запросы на выплату (Payout)

Мерчант через API создаёт заявку на вывод (адрес, сумма, сеть).
Заявка фиксируется в БД с уникальным номером и статусом, попадает в очередь.
Обработка: ручная или полуавтоматическая (с проверками и подтверждением оператора и выбор с какого кошелька платить).
После выполнения/отклонения статус обновляется. Мерчант может запросить статус заявки по номеру.
Цель — безопасность, контроль и полный audit trail выводов.

5. Требования к интерфейсу и безопасности (кратко)

- Удобный переключатель между магазинами в кабинете.
- Визуальные индикаторы текущего режима.
- История платежей и заявок на выплату по каждому магазину.
- Безопасное хранение API-ключей, логирование всех действий, rate limiting.
- Верификация домена при подключении (рекомендуется).

6. Интеграция с ядром платформы

Модуль использует уже существующую систему генерации кошельков и мониторинга транзакций. Внутренние балансы магазинов ведутся в едином ledger платформы. Личный кабинет расширяется новыми разделами.

7. Заключение

Модуль позволяет мерчантам быстро подключать приём криптовалюты с гибким выбором модели адресов (постоянные или временные) и надёжным механизмом вывода средств. Документ является основой для дальнейшей детализации (API-спецификация, схемы БД, интерфейсы) и может быть доработан.
